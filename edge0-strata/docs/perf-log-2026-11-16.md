## Pareto 0 - the GPU fence protocol: it is why the box dies, and it outranks every speed item

**This is not a commit-limit or VRAM problem.** The evidence rules both out:
the pagefile's `PeakUsage` is **0** (never used, in 4 GiB allocated), there is no
Resource-Exhaustion event, no bugcheck, no Minidump, no MEMORY.DMP, no WHEA
record and no display-driver TDR (4101). `PowerButtonTimestamp = 0` and
`LongPowerButtonPressDetected = false`, so it was not a power-button reset.
Event 6008 puts the stop at **14:50:02**, and `bench32k.log` was last written at
**14:49:39** - 23 seconds into the 32K prefill.

Three faces of one defect:

**A. A GPU spin is used as a fence.** `wait_flag_ge_kernel`
(`src/kernels/cuda/verify_kernels.cu:1224`) is

```cuda
while (*flag < value) strata_spin_pause();   // no timeout, no escape, no error word
```

launched `<<<1,1>>>` on the compute stream from 19 sites in `verify.cpp`
(1517, 2486, 2502, 2539, 2562, ...), **inside the captured layer graphs**. It is
the interlock that tells the GPU "the CPU's share is in the mapped rows". Its
own sibling `wait_handoff_kernel` (same file, line 1245) is *bounded*:
`timeout_ns` plus an `err` word in mapped memory, and the comment says why -
"the host fails the window instead of using a stale hand-off" and "the graph
completes and no stream is left hanging". **The correct pattern already exists in
this file; `wait_flag_ge` simply does not use it.** A one-wavefront infinite spin
on the GPU that drives the display is unrecoverable - which is exactly the crash
signature above.

**B. The host side times out, the device side does not.** `latent_cpu_run`
(`src/core/expert_source.cpp:4956-4963`) waits on the D-stage doorbell from the
host with a **20 s** timeout and a clean error. The GPU waits on the same class
of handshake forever. Two ends of one handshake must expire together.

Reachable ways the GPU can wait forever: `latent_cpu_run` returns early on error
before any publish (`expert_source.cpp:5040`, `4958`); the `d.stale_x` path
(`5432-5438`) deliberately skips the publish when the device residency table
says every routed expert is resident - which the engine *counts* as
"layer-windows with CPU experts and no activation published"; and
`STRATA_ROUTE_TAIL_SKIP` entries (`kind == -2`, no work) are covered by the
`_or` variant's `skip_` word but not by the plain `wait_flag_ge` at
2486/2502/2562.

**C. A driver fence object per 1.16 MB blob.** `prefill.cpp` uses one
`cudaEventRecord` plus two cross-stream `cudaStreamWaitEvent` **per expert**
(3708/3799/3836), re-arming the ring events `m.copied[]` / `m.used[]` every
entry. Measured at 80 us/record and 45 us/wait: 63,734 records + ~127,000 waits
= the 10.6 s the profile calls `wait copy`. A 32K prompt multiplies the chunk
count ~8x (order 1.2M fence operations) **while** the CPU pool's work also grows
8x - the two converge, which is why 4K survived and 32K died 23 s in. The
bounded, coalesced version of this primitive also already exists:
`handoff_publish_kernel` (verify_kernels.cu:1259) counts with `atomicAdd` and
raises **one** flag per group, not one fence per blob.

**The 14:41 crash in `ucrtbase.dll` is the engine's own watchdog, and it shows
the recovery is not machine-safe.** `Event 1000` reports `strata.exe`,
`ucrtbase.dll`, exception `0xc0000409` - `STATUS_STACK_BUFFER_OVERRUN`, which is
what `std::abort()` raises on MSVC via `__fastfail`. `verify.cpp:3911-3915`
shows the deliberate sequence on a failed expert upload: `release_gpu_waits(5000)`
then `std::abort()`. `verify.cpp:1294` records the same signature being observed
before: "no progress for 85 s, then the watchdog's 0xC0000409". So the watchdog
fires ~85 s after the GPU stops making progress - and when it fires with 26.66
GiB pinned and the display GPU already wedged, Windows cannot recover, hence the
14:50 hard stop.

### Fix order

1. **Bound `wait_flag_ge_kernel` the way `wait_handoff_kernel` is bounded**
   (`timeout_ns` + an `err` word the host checks, failing the window). Smallest
   diff, and it converts a machine freeze into an error message.
2. **Make the publish unconditional**: every error path in the CPU pool raises
   the flag with zeroed rows, so the GPU is always released.
3. **One handshake per group flush** in the prefill streamed walk, not one fence
   per blob; and never re-arm an event a pending wait still references.
4. **Bound the host-side `cudaEventQuery` spins** (`verify.cpp:5472`, 5204,
   5362, 5421) the same way - a spinning thread that must also submit the work
   that signals the fence can livelock.

Not a fix: raising the pagefile, or shrinking the KV. Neither is on the path.

The reference the user set for this class of box ("16 GiB VRAM + 20 GiB RAM")
is 430/778 prefill and 62/73 decode. So prefill is **4.6x** off and 4K decode
is **2.7x** off - not 20x. The 20x impression comes from the 32K decode,
which is cache-starved (see Pareto 2).

Two facts:

1. **The expert GEMM runs at 395 GFLOP/s** - 1.5% of this card's ~26 TFLOP/s
   FP16 peak. 1.95M (token, expert) pairs x 4.92 MFLOP = 9.6 TFLOP over
   15147+9172 ms. Q3_K unpacking is real work, but not 60x of it.
2. **The expert stream runs at 1.56 GB/s** (74 GB / 47.4 s) against a link
   measured at 28 GB/s - **18x below**. 22% of the whole prompt is the GPU
   idling in `wait copy`, and another 12% is `gather` (the device-side
   scatter into group buffers, running at ~13 GB/s).

### Why the stream is 18x off: an 8-slot ring, and a submission per blob

A 4K prompt is read in **512-token chunks** (`prompt chunk auto: 512`). The
deep streamed ring only engages at `stream_all_min() == 1024` tokens per
chunk, so a 4K prompt takes the *staged* walk with `STAGE = 8` slots - 9.3 MB
in flight. The comment at `prefill.cpp:3734` already names the second half of
it: **under WDDM every `cudaEventRecord` is ~80 us and every cross-stream wait
~45 us**, and the default path pays one of each (issuer side) plus one wait
(consumer side) *per expert*. 63734 experts x ~170 us = **10.8 s**, which is
`wait copy` almost exactly.

Two documented knobs exist for this and are OFF by default:
`STRATA_PREFILL_COPY_EVENT_EVERY=N` (one copied event per N experts) and
`STRATA_PREFILL_COPY_WAIT_DEDUPE=1` (one wait per release event).

**61% of decode is two stages.** Both are handoffs between the GPU and places
the GPU cannot see:

- **`hc1 up`** is not a hyper-connection up projection despite its name. It is
  the boundary stamp `stamp(l, 32)` ("the FFN-side read ends here, the router
  starts"), so it carries the whole latent **D stage**: quantize x, `iq_mmvq`
  of the D matrix for the layer, the column scales, two `quantize_*_rows`, and
  **two `cudaMemcpyAsync` D2H** into mapped host memory plus the xl doorbell
  (`verify.cpp:2197-2224`). Its mirror `hc0 up` - a real up projection - is
  1.20 ms, 16x cheaper.
- **`copy+combine`** carries `copy_from_mapped(...)` - an H2D of the CPU
  experts' output rows out of mapped host memory - and then the combine
  kernel. At T=1 that is **102 KB per layer, 4.9 MB per token, in 17.5 ms =
  280 MB/s**: one small H2D per layer, 48 times, each paying the WDDM
  submission plus copy latency.

The D and U tables themselves are in VRAM (2.55 GB, `latent_dense_q8.bin`):
per token the D stage reads 26.2M params x 48 layers = 1.34 GB and the U stage
the same again, so ~2.7 GB of VRAM traffic - ~8 ms at this card's ~330 GB/s.
That is the decode floor's larger half; the small-copy latency is the rest.

the reference 430 tok/s item 1 must also fall ~3.5x.

### The chunk size multiplies the expert traffic (and it is chosen for VRAM, not traffic)

63734 blobs over 8 chunks x 48 layers = **166 distinct experts per layer per
chunk** out of 512, for 512-token chunks. The count of chunks therefore sets
the expert traffic directly:

    traffic = (prompt_len / chunk) x 48 layers x distinct_experts(chunk) x 1.16 MB

The 4K prompt: 8 chunks x 48 x 166 x 1.16 MB = **74 GB**.
The 32K prompt at the auto chunk of 1024: 32 chunks, and a 1024-token chunk
routes to many more of the 512 experts - so the same 26.7 GB expert set is
streamed *dozens of times*. This is why a long prompt is not 8x the 4K prompt
but far more. **The auto chunk is sized by VRAM, never by this traffic**, which
is the wrong objective on a box whose link is the bottleneck: a 4x larger chunk
is 4x fewer passes over the expert set.

**Therefore the ranking of the served decode is not the T=1 ranking.** At T=4:

1. **`copy+combine` 40.22 ms = 41.1%** - the CPU experts' rows coming back into `parts` and being

### What `copy+combine` contains, and why its rate is the defect

Slot 24 spans **two** things under one stamp: `copy_rows_from_mapped` / `copy_from_mapped` (the
CPU rows crossing PCIe into `parts_out`) and the combine kernel. For scale:

| T | bytes per layer (n x K x N x 4) | ms per layer | implied rate |
|---|---|---|---|
| 1 | 102 KB | 0.365 | 280 MB/s |
| 2 | 205 KB | 0.461 | 445 MB/s |
| 3 | 307 KB | 0.685 | 448 MB/s |
| 4 | 409 KB | 0.838 | 488 MB/s |

`pcie_probe` measures 28.5 GB/s for exactly this kind of pinned-mapped copy, and 82 us for a 52 KB
one with a full sync. So the transfer is not the mechanism's limit: **a roughly fixed ~0.25-0.3 ms
per layer sits on top of it**, which is either graph-node cost or the combine launch. That is a
question this instrument cannot answer, because one stamp covers both. **Splitting slot 24 into a
copy stamp and a combine stamp is the next trap to build** - per the workflow, when a measurement is
inconclusive, go back to instrumentation rather than guess.

### Long context: what the KV format is worth, and what it is not

Measured ceiling with the 64-token-prompt probe (`scan_ctx.bat`), ascending, `--kv turbo3`:

| context | result | session VRAM |
|---|---|---|
| 32768 | **RUNS** | - |
| 65536 | **RUNS** | - |
| 98304 | **RUNS** | - |
| 131072 | **RUNS** | - |
| 196608 | refuses | KV 1360 MiB, 747 MiB short |
| 262144 | refuses | KV 1773 MiB, 1324 MiB short |

Session VRAM at 262144 tokens by format (`scan_ctx.bat <fmt> 262144`):

| format | session | B/cell | vs turbo3 |
|---|---|---|---|
| int8 | 3741 MiB | 14970 | +1968 |
| q4_0 | 2301 MiB | 9208 | +528 |
| rot4 | 1917 MiB | 7671 | +144 |
| **turbo3** | **1773 MiB** | **7094** | **0** |

Two independent checks pin the geometry: `int8 - q4_0 = 1440 MiB` and `(264-144) x 2 x n_head_kv x 262144`
agree only at **n_head_kv = 24`; and `q4_0 - turbo3 = 528 MiB` matches `(144-100) x 2 x 24 x 262144 = 554 MB`
to within rounding. So turbo3's KV is 4800 B/cell of the 7094 B/cell session:
**the KV format controls 68% of the long-context cost, and 32% of it does not respond to the KV format at all.**

**Past ~200K the format stops being the lever.** The only mechanism that reaches further is
`--kv-resident N`, which keeps N cells in VRAM and the rest in pinned host RAM:

| context | config | result |
|---|---|---|
| 262144 | turbo3 + `--kv-resident 65536` | **RUNS** (367 expert slots) |
| 524288 | turbo3 + `--kv-resident 65536` | refuses: session 1328 MiB, **910 MiB short** |
| 524288 | rot4 + `--kv-resident 65536` | refuses: session 1364 MiB, 971 MiB short |
| **524288** | **turbo3 + `--kv-resident 65536` + `--spec 2` + `--vram-reserve-mib 300`, no MTP** | **RUNS** |

The last row is the working configuration, from its own log line:

```
strata generate: KV streaming: 65536 of 524288 cells per QSA layer in VRAM, the K/V in 2.34 GiB of pinned RAM
strata generate: expert cache auto: 1.54 GiB free, 300 MiB reserved (+0 MiB for the draft head) -> 922 slots
```

**This is where turbo3 earns its place.** The streamed part is 458752 cells x 2 x 24 heads: 2.34 GiB of pinned
host RAM at 100 B/head, against 5.81 GiB at int8's 264 B and **11.3 GiB at f16**. With 26.66 GiB of experts
already pinned, 11.3 GiB does not fit on a 48 GB box - so at 512K the format is not a speed/capacity nicety, it
is the difference between a configuration that exists and one that does not. `rot4` would cost 2.62 GiB and
also fit; `q4_0` 3.16 GiB; `int8` does not comfortably.

Costs of that configuration, stated plainly:

- **No MTP** - the draft layer (795 MiB) and its head (281 MiB) are what paid for the expert cache, so there is
  no speculation and decode runs single-token windows: `wait for rings 372 ms/round` at 512K depth, i.e. ~2.7
  tok/s. That is a reading configuration, not a chat configuration.
- **KV streaming misses**: only 65536 of 524288 cells are resident, so attention at 512K depth pays PCIe for the
  non-resident cells - visible as the 372 ms/round against 54 ms/round at 4K.
- 922 expert slots and a 1.00 GiB cache, i.e. no worse than 4K's 819 thanks to what streaming freed.

### Caveat that no amount of KV compression removes

`--yarn-orig-ctx` defaults to 262144 - the context the model was trained on. Bytes for 512K fit only after the
VRAM above is freed, and **beyond 262144 positions the model needs rope scaling** (`--rope-scaling
linear|yarn`), which changes quality and is not measured here. Fitting 512K and producing coherent text at 512K
are two different claims.

## The prefill breadcrumb trace, and the 1/6

New instrument: `STRATA_PREFILL_TIMING=1` now prints a **component table with marks, device ms and host ms**
(the host column is new - it charges the host time between two marks to the phase that was open, the same rule the
event gap uses). `STRATA_LATENT_NPROF=1` times the A-stage function itself.

Measured (4K prompt, `tr_512.log`; this run had NPROF on, which syncs per call, so its 65 s wall is perturbed -
the unperturbed baseline is 43.9 s / 92.6 tok/s):

| component | marks | dev ms | %dev | host ms |
|---|---|---|---|---|
| **gemm gate/up** | **64126** | 21658 | 33.3% | 37739 |
| **gemm down** | 384 | 12691 | 19.5% | 2 |
| **gather** | 384 | 11095 | 17.1% | 20 |
| **wait copy** | 63511 | 5218 | 8.0% | 1162 |
| gdn | 288 | 4902 | 7.5% | 18 |
| qsa proj / attn | 192 / 96 | 1487 / 869 | 3.6% | 10 |

| hc write / router+shared / combine | | ~2200 | 3.4% | 43 |

**The `marks` column is the finding.** `gemm gate/up` has **64,126 marks** - it is entered once per expert. And
the A-stage function probe agrees exactly:

```
latfq3kprof: calls=64080 ms=10742 entries=1948496 us/entry=5.51
```

1,948,496 entries over 64,080 calls = **30 entries a call**, i.e. **one expert per launch**. `lat_q3k_fused`
splits the 640 gate/up features over `kItems = 5` blocks, so each launch is **5 blocks**. On a 20-CU card that is
at most 25% of the GPU, and for the tail flushes (`last: nb=1 ent=1`) it is one block.

`lat_q3k_fused` already accepts `n_groups` and a per-group `counts` array and sizes its grid as
`dim3(kItems, min(n_groups, 512), gz)` - **batching is supported by the kernel and not used by the caller.**
The MMQ branch directly above it already batches: `MMQ_GROUP = 64` experts per launch, flushed on
`lat_q == lat_gmax` and on a row cap (`prefill.cpp:5997-6009`). **The fused branch has neither accumulator nor
flush, so `nb` is 1 every time.**

## Why a bigger chunk is slower (the "auto chunking" question)

| chunk | prefill tok/s |
|---|---|
| **512 (auto at 4K)** | **91-93** |
| 1024 | 71.24 |
| 2048 | 42.63 |

Phase comparison at 2048 vs 512 (`tr_2048.log`): `gemm down` 40,295 ms vs 12,691 (3.2x per entry, same entry
count), `gather` 26,278 vs 11,095 (2.4x), while `gemm gate/up` *falls* 21,658 -> 10,342 and `qsa attn` rises
869 -> 2,407. So the chunk does not scale proportionally: two phases explode and one improves.
`moe_bufs()` sizes the latent buffers from `T*K` (`group_bytes(T*K, ...)`, `act_bytes(T*K, 640)`), so at T=2048
the buffers are 4x and the expert cache is starved; `gather` and `down` then pay for it. **The auto chunk is
right to stay at 512 on a 12 GB card - this is a VRAM-budget effect, not a batching one.**

## How much expert can actually be trimmed

From `--dump-routing` (`routing_trim.py`, 1,920 records = 48 layers x 40 positions, k=10 - a 40-position
sample, not the full prompt):

| keep ranks | entries dropped | distinct (layer,expert) pairs dropped | blob bytes |
|---|---|---|---|
| 0..7 (R=8) | 20.0% | **13.7%** | ~1 GiB |
| 0..6 (R=7) | 30.0% | 20.8% | ~1 GiB |
| 0..8 (R=9) | 10.0% | 7.0% | ~0 GiB |
| 0..5 (R=6) | 40.0% | 29.3% | ~2 GiB |

The byte-relevant number is the *pairs* column, not the entries one: a distinct expert costs one 1.16 MB blob
whether one token routes to it or thirty. **So `--kv turbo3`-style gains do not come from a rank cut: keeping 8
of 10 ranks removes 20% of the entries but only 13.7% of the bytes.** R=7 (20.8%) is the most aggressive cut
that is still defensible, and it is worth about a fifth of prefill's expert traffic - real, but it does not
close a 6x gap, and it changes the output.

## The staged-launch batching experiment: measured, then rejected

**Hypothesis.** `gemm gate/up` had 64,126 marks for one 4K prompt - one A-stage launch per expert - and
`lat_q3k_fused` spreads its 640 gate/up features over `kItems = 5` blocks, so a one-expert launch cannot fill the
card. `arm_launch` also does three small H2D uploads (gp, gs, la_n) per call through `up_ring`, which blocks on a
slot's event. Batching consecutive staged experts into one launch should cut both.

**Result (walk 2, `prefill.cpp` "A: the resident experts share grouped launches").** The batching did exactly
what was predicted:

| | before | after | |
|---|---|---|---|
| `gemm gate/up` marks | 64,126 | **8,279** | 7.7x fewer launches |
| `gemm gate/up` dev ms | 21,658 | **8,088** | -63% |
| `gemm gate/up` host ms | 37,739 | **2,342** | -94% |
| prefill wall | 65,949 | **51,878** | -21% |
| prefill tok/s | 61.58 | **78.27** | +27% (both perturbed by timing on) |

**And it was rejected, because the output changed.** Baseline tokens are
`248046 198 248045 74455 198 248068 198 760 1156 ...`; the batched run produced
`220 248046 198 248045 74455 198 248068 271 248069 ...` - divergent from the first token.

**Root cause of the wrongness.** `lookahead = STAGE - 1` (`prefill.cpp:7174`) and the staging ring is
`STAGE = 8`, so the staged walk already spends **every slot** on lookahead. Holding a second blob makes
`stage_one()` reuse a slot whose blob the pending launch still reads. There is no free slot for a batch, by
construction.

**Prerequisite for doing it properly**, in this order:
1. enlarge the staging ring (`STAGE`, and the `stage_dev` / `used` / `copied` / `used_of` allocations that
   follow `m.ring`), and
2. change `lookahead` from `STAGE - 1` to `STAGE - batch` so `batch` slots are genuinely free, then
3. batch, and accept only on bit-identical tokens.

The code now defaults `STRATA_LAT_STAGED_BATCH` to **1** (the old per-blob behaviour) and the comment on that
knob says it is not safe to raise until 1 and 2 land. The walk-1 batching (the other branch, taken at other chunk
sizes) *is* retained: it produced bit-identical tokens.

## What the host column exposed (this is the bigger finding)

With host time attributed per phase, prefill's wall is not GPU time:

| | dev ms | host ms |
|---|---|---|
| host grouping | 248 | **26,046** |
| wait copy | 6,063 | **22,852** |
| gemm gate/up | 8,088 | 2,342 |

`host grouping` is 26 s of host time for **248 ms** of marked device time - the expert grouping preparation, not

Before this column existed, all of that was invisible: it looked like "the GEMMs are slow".

## Pareto 2 - decode at the window width that is actually served (T=4)

| # | item | share (T=4) | cumulative | root cause | fix |
|---|---|---|---|---|---|
| 1 | `copy+combine` | **41.1%** | 41.1% | ~0.25-0.3 ms/layer of fixed cost on top of a 409 KB mapped-memory H2D running at 488 MB/s; one stamp covers both the copy and the combine, so the split is not yet measured | split the stamp (trap first), then: one `cudaMemcpyAsync` H2D of the whole `n*K*N` range instead of a per-row gather, and fold `moe_hit_add` into the combine (`STRATA_FUSE_HITS=1`, gfx12-only by default) |
| 2 | `hc1 up` (the latent D stage) | **24.8%** | 65.9% | fixed ~0.4 ms/layer: quantize, `iq_mmvq` of D (1.34 GB/token of VRAM), 2 quantize_rows, 2 D2H, doorbell - all on the serial compute stream | move the two D2H copies (host consumers only) off the critical chain; both are already covered by the `m_xlseq_` doorbell |
| 3 | everything else | 34.2% | 100% | 48 layers x ~0.5 ms of small GEMVs, none above 4% | fewer launches per layer |

The T=1 ranking I first published (hc1 up 32.5%, copy+combine 28.6%) is superseded by this one,
because `copy+combine` is the stage whose cost tracks the window and the served decode runs T=2..5.

**The expert cache is not on this list, and cannot be.** 24576 experts x
1.16 MB = 28.5 GB of A blobs against 12 GB of VRAM: at 4K the cache holds 2.8%
of them, at 32K 1.2%. Even a cache that took every free byte would reach ~40%,
and each hit is worth ~0.37 ms of the 61.

## The 93 -> 65 tok/s question: bisected out of the engine

After the staged-launch experiment was rejected, the rebuilt engine ran at
65.0 tok/s where the 15:14 baseline ran 93.0, with **bit-identical tokens**
(`248046 198 248045 74455 198 248068 ...` in both). Every log on disk orders
the change precisely:

| log | time | chunk | prefill | decode |
|---|---|---|---|---|
| `rep_turbo3_2` | 15:59 | 512 | **88.53** | **19.85** |
| `pf_A_1024` | 16:21 | 1024 | 71.24 | **5.04** |
| `tr_512` | 16:36 | **512** | **64.99** | 5.06 |
| `rev_A` (now) | 17:36 | 512 | **65.00** | 5.06 |

`tune_P1_chunk1024` at 15:17 also ran chunk 1024 at **114.69** tok/s, so even
the same chunk size lost 38% between 15:17 and 16:21. The only things that ran
in that window were the 32K -> 512K context probes and the KV-size sweep, and
the prefill edits under test landed *after* 16:31 (chunk 512: 64.99 before the
edit, 65.00 after - a 0.01 tok/s difference). **The regression is not in the
prefill code.**

What the hardware says right now (`pcie_probe.exe`, staged ROCm 10.2 runtime):

| probe | recorded ceiling | now | delta |
|---|---|---|---|
| streaming H2D 1 GiB | 28.17 GB/s | **21.65** | -23% |
| streaming D2H 1 GiB | 28.54 | **23.20** | -19% |
| pipelined 900 x 1.14 MB | 27.89 | **18.35** | **-34%** |
| serialised one sync/blob | 11.08 | 10.81 | -2% |

Prefill is -30%; the pipelined host->device rate is -34%. Ruled out, with the
instrument rather than by argument:

- **not contention**: no other process holds the GPU (1.3% engine utilisation,
  200 MB VRAM), 42.7 GB RAM free, pagefile 22 MB used;
- **not a driver reset**: no TDR (event 4101) today - the one Display event is a
  12:49 `SetDisplayConfig` note;
- **not memory instability**: zero WHEA-Logger errors today, and the CPU expert
  pool still reads **31.7 GB/s** (baseline 30.6), so host DRAM is unchanged;
- **not the link width**: the card is still PCIe 4.0 x16 (`CurrentLinkSpeed 4`,
  `CurrentLinkWidth 16`);
- **not determinism**: two identical runs (`det_A1`, `det_A2`) produce identical
  tokens, so the engine is deterministic and token equality *is* a valid gate
  when the instrumentation flags also match.

Decode moved much further than prefill and does not share its cause: the CPU
pool is flat (27.49 vs 27.60 ms/round) while `wait for rings` goes
**53.85 -> 353.67 ms/round** and MTP drafting **5.22 -> 64.65 ms/round**. Both
of those are host->device expert-blob waits, i.e. the same DMA path the probe
measured - but 6.5x, not 1.34x, so there is a second factor in the ring itself
still to find.

**Consequence for every number above it:** the 93.0 tok/s baseline is not
reproducible on the current machine state. Ratios measured *within* one
session are valid; absolute tok/s across the 16:00 boundary are not.

## Correctness gate: compare against the Kraken-x oracle, not against tokens

Token equality proved the batched prefill wrong, but it is a weak gate: it
needs matched instrumentation flags (the speculation policy adapts to measured
latency, so `STRATA_PREFILL_TIMING=1` alone changes the text), and it says
nothing about *how far* a change moved the arithmetic.

`third_party/Kraken-x/include/krk/turbo_kv.hpp` is a complete CPU reference for
both codecs, and `tools/turbo_kv_selftest.cpp` proves the shipped centroid table
by re-solving the Lloyd-Max optimum rather than trusting it. Comparing the two
implementations settles the port exactly:

| | Kraken-x reference | this port | |
|---|---|---|---|
| turbo3 row, d=256 | `ceil(d/8)*3` codes + f32 sigma = **100 B** | 100 B | same |
| turbo3 sigma position | **trailing** | **leading**, 4-aligned | deliberate |
| turbo3 centroid table | `kTurboCentroid[8]`, 7 boundaries | same values | same |
| rot4 row, d=256 | `(d/32)*14` = **112 B**, 3-bit Lloyd-Max per 32 | 112 B | same |
| rot4 block | f16 scale first, then 12 code bytes | same | same |
| rotation | FWHT over power-of-two chunks, per (layer, head) seed | see `kv_turbo.cu` | to verify |

The gate to add: quantize the same random rows with `krk::pk_quant_row` on the
host and with the GPU codec, then require the **row bytes to match bit for bit**
once the sigma is moved to its documented place. That is an exact oracle - it
fails on a single wrong code, a wrong table entry, a wrong boundary or a wrong
seed, none of which token equality can localise.

**Result: the oracle is green, and the codec is correct on both paths.**
`kv_turbo_parity` (arm `[6/6]`) against `krk::pk_quant_row`, 64 rows /
16,384 coordinates each: turbo3 **0 of 16,384 code bytes differ** with 13 of 64
sigmas off by 1 ULP (rel 8.4e-08), margin to the nearest Lloyd-Max boundary
1.633e-05 against 3.289e-07 that the sigma difference could move it -> **50x**;
rot4 **0 code bytes and 0 sigmas**. Prompt (batch) and decode (per-step) appends
agree byte for byte: 0 of 6,400 and 0 of 7,168.

An earlier revision of that test reported "99% of the batch output is wrong".
That was **the harness, not the kernel**: it passed `Ky.data()`, a host pointer,
to a kernel that dereferences device memory, and on this stack a host pointer
does not fault - the GPU reads host RAM through the PCIe window and returns
plausible garbage. `need_device_ptr()` now refuses that call (exit 2). The
engine was never affected: production prefill passes `m.Kc` from `Alloc::take`,
which is `cudaMalloc`/device-arena memory.

## Prefetch depth and "out of order scaling": measured, and neither is the lever

Two proposals were tested in the only form this hardware has: more experts in
flight, and fewer submissions per expert. Same session, `STRATA_PREFILL_TIMING=1`
in both A/B arms, 4,063 tokens, 48 layers.

| chunk | ring in flight | wait copy | gemm gate/up | gemm down | gather | prefill |
|---|---|---|---|---|---|---|
| **512 (auto)** | **STAGE = 8 slots, 9.3 MB** | 11744 ms (17.4%) | 17810 | 12424 | 11004 | 67.45 s / 60.24 tok/s |
| 1024 | 538 slots, 624 MB | 6375 ms (11.0%) | 12734 | 11279 | 11308 | 58.03 s / 69.98 |
| 1024 + one copied event per 8 + one wait per release | 538 slots | 6139 ms (10.7%) | 12359 | 11290 | 11326 | 57.43 s / 70.74 |

Without the timing flag the same pair is 62.46 (512) vs 71.24 (1024), and 2048
collapses to 41.4-42.6 (it does not fit the VRAM budget: the ring and the
`stream_all_min()-1` row buffers stop paying for themselves).

What the table says:

1. **A deeper prefetch window is worth 16%, and it is already built.** The
   shipped auto chunk is 512, which is below `stream_all_min() == 1024`, so
   `stream_all` is false and the prompt takes the staged walk: `STAGE = 8`
   slots (9.3 MB) and one WDDM `cudaEventRecord` + cross-stream wait per
   expert. 63,500 experts x ~170 us is exactly the `wait copy` column. At 1024
   the threaded issuer keeps a whole 538-slot ring ahead and `wait copy` falls
   to 11%.
2. **Beyond that, the copy engine is not the constraint.** Batching the
   submissions on the deep ring (`STRATA_PREFILL_COPY_EVENT_EVERY=8`,
   `STRATA_PREFILL_COPY_WAIT_DEDUPE=1` - inert at 512 because they are gated on
   the threaded issuer) buys **1.1%** and moves `wait copy` by 236 ms of 57 s.
   A second prefetch unit, or a deeper window, has nothing left to overlap:
   the remaining 6.1 s is data that has not arrived, not queueing.
   (`STRATA_PREFILL_RING=512` vs the natural 538 was also measured: 62.57 vs
   62.46 tok/s.)
3. **There is no separate scaling stage to reorder.** The `dequant` phase
   exists in `PfTimer` and **never opens** - zero marks in every run above. The
   Q3_K/IQ4_NL scale is folded into the quantized dot product, so "out of order
   scaling" would reorder nothing. Where scales are separate (the turbo3/rot4
   KV codecs) they are one multiply per row, already inside the kernel.

The three expert kernels are 61% of the 1024 timeline (12.4 + 11.3 + 11.3 of
57.4 s) at ~395 GFLOP/s, which is 1.5% of this card's FP16 peak. Prefetch and
scaling units both address the 10.7%, not the 61%.

One dead end found while checking the launch counts: `gemm gate/up` fires
**one launch per expert** (64,126 at chunk 512, 34,642 at 1024) because the
engine's own batched `WideBatch` walk is unreachable on HIP - `lat_dev()` sets
`ok` only inside `#if !defined(__HIPCC__)` (`moe_fused_q3k.cu:1404`) and the
q3k batch kernel is a CUDA-only `mma.sync` body (`:1577-1583`). The
"latfusedq3k: the A stage runs lat_q3k_fused" line is true but describes the
*per-expert* entry point. Batching it on gfx1031 needs an RDNA2 kernel, not a
flag: gfx1031 has no WMMA, so it is a real kernel project and not part of this
measurement.
