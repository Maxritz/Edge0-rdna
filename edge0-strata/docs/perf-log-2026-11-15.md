# Perf log — 2026-11-15 (RDNA2 gfx1031, Edge0-120B q3k)

All numbers are measured on this machine with `serve/config-rdna2.json`
(120B MoE, `--kv int8`, `--max-context 2048`, MTP `--spec 4`). Prompt unless
stated: `We need answer user. User statement: ` (60 tokens), greedy,
32 tokens generated.

## Landed

### 1. fp8 (e4m3) dot2 GEMV path — `STRATA_DOT2=1`

`src/kernels/cuda/native_bf16.cu`. `bf16_gemv_fp32_mmvf(_multi)` dispatches
the RDNA2 `V_DOT2_F32_F16` kernels when the tensor's e4m3 image is in the
cache (`warm_fp16_cache` at `Verifier::init`, 74 tensors / 110 MiB, name
whitelist + 512 MiB budget, `output.weight` never). Weights unpack
e4m3→fp16 with exact bit math; activations pack with
`V_CVT_PKRTZ_F16_F32` (RTZ). Fallback to the scalar kernel when any weight
exceeds e4m3 range.

| run | prompt tok/s | gen tok/s | VRAM free @ request |
|---|---|---|---|
| dot2 off | 24.8 | 26.6 | 819 MiB |
| fp8 dot2 on | 24.6 | 26.0 | 445 MiB |

**Verdict: a wash on speed, a win on footprint** (1 B/weight image instead of
2 B; the earlier *fp16* image version converted all 484 tensors, took the
card to 0 MiB free and cost 27%). The MMVF-routed stages are only ~15 ms of
the 94.65 ms decode window, and the unpack costs what the halved traffic
saves. Keep it opt-in.

### 3. INT8 K/V rotation (`STRATA_KV_ROT=1`) — refused with a cache

Rotation itself is sound: `kv_hybrid_parity` passes all 6 checks including
the FWHT→quant→dequant→inverse round trip. In the full engine, however, a
**fresh prompt and the same prompt resumed from a mid-prompt checkpoint
produce different (each self-consistent) greedy text**, reproducibly:

```
run1 (0 reused, 60 read)   -> "We need respond to user: ..."   (matches the unrotated baseline)
run2 (55 reused, 5 read)   -> "We need answer user. ..."
run3 (55 reused, 5 read)   -> == run2                          (resume is deterministic)
```

So the resume path is where rotated cells and the rotation convention
disagree. Until that is fixed, `generate.cpp` **refuses the combination**:

```
strata generate: STRATA_KV_ROT=1 is not used: rotated INT8 K/V is inconsistent
with resumed checkpoints (a fresh prompt and its resumed continuation disagree).
```

Verified: with the guard, `STRATA_KV_ROT=1` serve runs are deterministic again
and match the baseline text. Rotation without a conversation cache still
works (opt-in).

### Overlap experiments — the wait is the drive, not a shallow pipeline

The overlap question was tested directly on the same 702-token prompt. Seven
configurations, ~0.4% noise on this machine:

| configuration | prompt tok/s | read (ms) |
|---|---|---|
| baseline (defaults + F16 prompt GEMMs) | 92.8–93.1 | 7538–7568 |
| `STRATA_PREFILL_CPU_SHARE=0` | 93.1 | 7538 |
| `STRATA_PREFILL_STREAM_AHEAD=0` | 93.1 | 7538 |
| `STRATA_PREFILL_RING=256` (deeper DMA ring) | 92.9 | 7556 |
| `STRATA_PREFILL_RING=512` | 93.0 | 7548 |
| `STRATA_PREFILL_STREAM_MIN=512` | 89.9 | 7806 |
| `STRATA_PREFILL_STREAM_MIN=512` + `CPU_SHARE=0` | 91.5 | 7669 |

All output-identical to the baseline (`o_base` vs `o_s512c0` compared text).

**Why nothing moves:** the run reads 12 562 blobs of ~1.16 MB = **14.2 GiB** in
7.55 s, i.e. ~2.0 GB/s effective. The engine's own pack pre-fill measures the
same drive at **6487 MB/s** (0.4 s for 2089 slots), so 14.2 GiB / 6.5 GB/s =
**2.3 s** — which is, to the millisecond, the `wait copy` stage (2297 ms). The
wait IS the drive's service time, already partially overlapped with compute;
no ring depth, stream-ahead or CPU-share setting changes it, and a deeper ring
(512 slots ≈ 600 MB) buys nothing.

**Therefore the lever is bytes, not overlap.** Two GEMMs and the gather
(687 ms, 8.6%) are the only remaining *compute* targets in prefill.

### Can the bytes be cut? Routing rank says no (measured)

`STRATA_PRUNE_PLAN`/`STRATA_PRUNE_RECORD` drop experts that no token routes
above a rank. Recorded this prompt's routing (`STRATA_PRUNE_RECORD`), then
applied it (`STRATA_PRUNE_RANK=7`, i.e. only experts that appear exclusively
in top-k positions 8-10 are dropped):

```
strata prefill: STRATA_PRUNE_PLAN rank 7: 0 streamed experts replaced by a zeroed 1.11 MB stand-in blob (on)
streamed 12562 blobs        <- identical to the baseline run (12562), three runs in a row
```

**Zero experts qualify.** With 697 tokens at top-10 routing, *every* one of
the 12 562 streamed (layer, expert) pairs appears in some token's top-7, so
even a k=7 model would still read the same blobs. Blobs are already read
once per chunk and shared by all tokens that route to them (12 562 blobs for
~418 000 token-expert picks) — the per-token cost is already amortised.

Consequence: **no routing-rank or top-k change can reduce prefill's expert
bytes here.** The remaining levers are (a) a lower-bit expert pack (smaller
blob), (b) a faster drive, or (c) computing prefill on the GPU with the
experts resident (the expert-cache hit rate, not the stream).

## How large a context fits (measured, `auto` expert cache)

Each config started cleanly on this card; the cost shows as a smaller expert
cache, not as an out-of-VRAM error:

| `--max-context` | expert-cache slots | VRAM free after load |
|---|---|---|
| 2 048 (current) | 2 089 | 804 MiB |
| 8 192 | 2 002 | 1040 MiB |
| 32 768 | 1 663 | 804 MiB |
| 65 536 | 1 019 | 1040 MiB |
| 131 072 | 360 | 203 MiB (below the 1024 safe reserve) |
| 262 144 | — | **refused**: "no VRAM was left for the expert cache" |

- **Largest that starts: 131 072 tokens** (cache 360 slots, 203 MiB free — the
driver may page; not a safe serving size).
- **Recommended: 32 768** — 1 663 slots (80% of the 2 048-context cache), 804
MiB free, and the 702-token prompt reads **identically and at the same speed**
(92.8 tok/s) as it does at 2 048.
- 65 536 works but halves the cache (1 019 slots).

**What context actually costs:** 2 089 → 360 slots over 129 024 extra cells is
**~1 slot per 75 cells ≈ 14.9 KB of VRAM per context cell**. The INT8 K/V cell
itself is only **528 B** — 28× less. So the context limit is the indexer pool and
the per-cell window buffers, **not the KV cache**: a 3-bit KV codec (Kraken's
rot4, 224 B/cell) would save ~300 B of a ~15 KB cost, i.e. **~2% more context**,
not the 2.4× its compression ratio suggests.

A turbo3/rot4 codec was written and then **removed** on 2026-11-15 (see
`docs/turboquant-from-kraken.md`): the rotation and the codebook measured right
(MSE 0.034 / 0.033, 52 / 56 B per row) but the scales were never correct, and a
debug run faulted the GPU into a Windows `Error` state that needed a reboot. No
turbo kernel remains in the tree, so the paragraph above stands as arithmetic
only — there is no working sub-8-bit KV in this engine today.

## Prefill expert-cache hit rate, three runs in one server

Config `serve/config-rdna2.json` plus `STRATA_PREFILL_TIMING=1`; three ~702-token
prompts differing only in their first sentence (so each run really prefills and
none is served from the prefix cache: `0 reused` in all three). The counters in
the timing line are **cumulative since process start**, which the arithmetic
shows: run 2's `streamed` is run 1's plus its own.

| run | GPU timeline | `streamed` (cum) | per-run streamed | `resident` (cum) | per-run resident | hit rate | `wait copy` |
|---|---|---|---|---|---|---|---|
| 1 | 8 179 ms | 12 891 | 12 891 | 1 161 | 1 161 | 8.3% | 2 362 ms (28.9%) |
| 2 | 7 969 ms | 26 391 | 13 500 | 2 754 | 1 593 | 10.0% | 2 337 ms (29.3%) |
| 3 | 7 947 ms | 39 762 | 13 371 | 4 381 | 1 627 | 10.2% | 2 345 ms (29.5%) |

**The hit rate does not warm up, and the reason is structural.** One 702-token
prefill touches ~14 000-16 000 distinct blobs (streamed + resident); the expert
cache holds 2 089 slots, i.e. ~2.4 GB out of a ~16-18 GB working set. A repeat of
the same prompt therefore still misses ~90%, and `wait copy` sits at 2.34-2.36 s
in every run (29% of the prefill). Re-sending a prompt cannot help: the cache is
7-8x too small to retain a prompt's experts, so the only levers are fewer bytes
per expert (a smaller pack), fewer experts per token, or more VRAM for slots.
The cross-check is the byte rate: 13 500 blobs x 1.16 MB = 15.7 GB, and
2.34 s x 6.5 GB/s = 15.2 GB - the wait is the read, nothing else.

Timing build overhead, for like-for-like comparisons: 81.0 / 83.5 / 83.4 tok/s
with `STRATA_PREFILL_TIMING=1` against 92.8 tok/s for the same prompt in the
production config.

## KV cache quantisation: the quality / byte / speed trade (measured)

Four `--kv` formats, one binary (`serve/config-rdna2.json` with only `--kv`
changed), three short prompts of 16 greedy tokens each **plus** the 703-token
prompt, all compared against `--kv fp16`.

| `--kv` | bytes/cell | @2 048 | @32 768 | cache slots @32k | prefill (703 tok) | outputs vs fp16 |
|---|---|---|---|---|---|---|
| fp16 | 2 112 | 4.3 MB | 69.2 MB | 1 188 | 93.0 tok/s | baseline |
| int8 (default) | 1 056 | 2.2 MB | 34.6 MB | 1 663 | 93.2 tok/s | **identical** |
| k8v4 | 816 | 1.7 MB | 26.7 MB | 1 744 | 93.4 tok/s | **identical** |
| q4_0 | 576 | 1.2 MB | 18.9 MB | 1 839 | 92.6 tok/s | **identical** |

"Identical" is byte-for-byte equality of the whole reply text (reasoning plus
content) on all four prompts, greedy. Prefill speeds are within run-to-run noise
(±0.4 tok/s), so KV quantisation costs nothing measurable on this path.

**What it buys.** At 32k cells, `q4_0` is 18.9 MB against fp16's 69.2 MB and
the auto-sized expert cache keeps 1 839 slots against fp16's 1 188 — but those
numbers are not proportional to the KV bytes: the difference in KV alone between
fp16 and int8 is 35 MB (~30 slots), while the slot count moves by 475. The sizer
picks in coarse steps and the free VRAM stays at the 900-1 026 MiB reserve, so
treat "more slots with a smaller KV" as a real but not proportional gain.

**What it does not buy.** It does not move `wait copy`. That wait is the expert
blobs read from disk (15.7 GB per 702-token prefill at 2.34 s, section above);
K/V stays in VRAM and never enters that read. A KV format is therefore a memory
trade, not a bandwidth one: use it to fit a longer context or a larger expert
cache, never to speed up prefill.

## Long-context KV drill: int8 vs q4_0 on one growing conversation

`--max-context 8192`, one conversation grown over five turns of ~634 tokens each
(every request carries the whole history, so the serve stack reuses the cached
prefix: `638/1267/1896/2525 reused` and only the new turn is prefilled). Final
prompt: **3 159 tokens**.

| turn | prompt tok | new tok | prefill int8 | prefill q4_0 | decode int8 | decode q4_0 |
|---|---|---|---|---|---|---|
| 1 | 643 | 643 | 86.5 tok/s (7 433 ms) | 86.9 (7 401) | 1 009 ms / 24 | 1 112 ms / 24 |
| 2 | 1 272 | 634 | 89.7 (7 064) | 90.2 (7 030) | 858 | 918 |
| 3 | 1 901 | 634 | 86.0 (7 371) | 88.0 (7 204) | 935 | 911 |
| 4 | 2 530 | 634 | 84.5 (7 503) | 86.1 (7 360) | 920 | 1 114 |
| 5 | 3 159 | 634 | 85.5 (7 419) | 85.3 (7 435) | 827 | 780 |

**Per-token time does not move with context or with the KV format.** Prefill is
7.0-7.5 s for 634 new tokens at every depth, because it is bound by the expert
blobs, not by attention. Decode is 34-46 ms per token in both formats, and that
spread is speculative acceptance, not K/V: the MTP drafts accepted swing between
10 and 19 of ~16 per turn, and the per-turn ordering of int8 vs q4_0 follows
the acceptance count, not the format (turn 4: q4_0 worse with 10/17 accepted;
turn 5: q4_0 better with 15/16). To compare decode formats, fix acceptance
first - here it is not measurable.

**Quality: 4 of 5 turns byte-identical; turn 4 (2 530 tokens) diverges.** int8
echoed a prompt sentence (`We need answer user. User repeated pattern: "Turn 4
sentence 1 discusses the model and its context window."`) while q4_0 paraphrased
it. After that the two conversations hold different text, so turn 5's match is a
coincidence of the model's repetitive output, not evidence. This is the first
case in this work where quantised K/V changes greedy output: at 643-703 tokens
the formats were identical on every prompt, at ~2 500 they were not. One
divergence in five turns is a signal, not a measurement of quality loss - a
perplexity run over a fixed corpus is what would quantify it.

## Repeating the 2.5k divergence: it is a tie, not a q4_0 defect

The turn-4 divergence above was re-run with a **fixed** 2 512-token history, so
both formats saw byte-identical tokens (`--max-context 8192`, greedy, 24 tokens).

* Five repeats of the same 1 266-token prompt on a fresh server:
  **int8 produced 1 distinct reply in 5, q4_0 produced 2 in 5.**
* Depths 1-5, two reps each (conversation cache on and off gave the same answer):
  **int8 disagreed with itself at depths 2, 3 and 5**, **q4_0 at 2 and 4**. At the
  depth in question (2 512 tokens) q4_0's two reps gave different texts while
  int8's two agreed.

So the spread **within one format** is as large as the difference between the two
formats, and the same prompt's greedy answer depends on what the server served
before it. The turn-4 divergence was a near-tie flipping, not q4_0 degrading:
this stack's greedy decoding is not bit-reproducible under interleaved requests,
which makes prompt-level A/B of KV formats meaningless at this depth.

The suspected cause - MTP speculative decoding accepting a different number of
drafts - **could not be isolated**: `--spec` must be at least 2 for a native pack
(`it needs --native SHARD1, --spec T (T >= 2)`), and `--spec 0` refuses to start.
`logprobs` would have given the top-1 margin, but the engine returned none in 9
of 10 requests through this path.

**What would actually measure KV quality:** the engine's own `--dump-logits` on a
fresh process per format (same prompt, compare the top-1 margin), or perplexity
over a fixed corpus. Neither is exposed through `serve/`.

## Logits A/B harness (`tools/kv_logits_ab.py`) - working, first margins measured

What it does: tokenizes a fixed prompt with the config's own tokenizer, then runs
the engine once per KV format in a **fresh process** (no conversation cache, no
expert-cache history), reads the full logits row of the prompt's last position and
reports top-1 id, top-1 logit, top-2 and the margin, plus the cross-format deltas.
`--repeats` also answers the question the reply-level test could not: are the
logits themselves reproducible run to run.

Two dump paths: `--dump-logits` with `--logits-stride` (the last row is always
emitted) for a GGUF pack, and `STRATA_NATIVE_LOGITS` (the `NLG1` stream the native
head writes) for an IQ pack.

**The native write already existed.** `--dump-logits` does leave an empty file on
an IQ pack (`generate.cpp:184`), but the verify loop's first window writes the
prompt's own row through `STRATA_DUMP_FIRST_LOGITS` (`generate.cpp:18919`,
`ver.copy_logits(0, ...)`, one bare float32 row). A first attempt added a second
hook at the head call; the probe showed that hook never runs on a native pack
(the prompt path goes through the verifier, not `run_head`), so it was reverted -
no engine code changed. The harness now reads the existing hook's raw row.

### First margins (651-token prompt, `serve/config-rdna2.json`, `--max-context 2048`)

| arm | top-1 | top-1 logit | top-2 | margin | across 2 fresh processes |
|---|---|---|---|---|---|
| int8 | 248046 `<\|im_end\|>` | 23.042089 | - | 4.148411 | identical (spread 0.000000) |
| q4_0 | 248046 `<\|im_end\|>` | 23.362247 | - | 4.438866 | identical (spread 0.000000) |

Cross-format: **same argmax**, margin delta **0.290**, top-1 logit delta **0.320**
- about 7% of the margin. Neither format is close to flipping the token.

Two things follow. First, at this length KV format is a measurable but small
perturbation, and it is now measurable without decoding. Second, the logits are
*bit-identical across fresh processes within a format*, so the reply-level
non-determinism recorded above does **not** originate at the head - it enters
above this row (the verify/spec accept path, or how a prompt path leaves state),
which is why comparing replies could never have settled the KV question.

Caveat: one position, one prompt, 651 tokens (well under the 2048 cap). Longer
prompts - where KV quantisation error actually grows - are the next arms.

### Growth with length (500 / 1200 / 2040 tokens, all prefixes of one filler)

Two fresh processes per arm at 500 and 1200, two more at 2040 after a first
single-process series ("A"). `--max-context 2048` puts 2040 at the cap.

| tokens | int8 margins | q4_0 margins | within-format spread | cross delta | argmax |
|---|---|---|---|---|---|
| 500 | 3.8025, 3.8025 | 3.7279, 3.7279 | 0.000 | **0.075** (2.0% of margin) | same |
| 1200 | 11.577, 10.310 | 11.966, 11.388 | 1.268 / 0.578 | **0.388** (0.778 in an earlier pair) | same |
| 2040 | A 8.726; B 7.940, 8.598 | A 5.336; B 6.454, 6.124 | 0.659 / 0.330 | **3.390** (A pair), **1.486** (B pair) | same in all 5 runs |

**The delta does grow with length - 0.075 -> ~0.4-0.8 -> ~1.5-3.4 - but above
500 tokens it is no longer separable from the engine's own run-to-run noise.**
At 500 tokens both formats are bit-reproducible across processes and the
difference is 2% of the margin. At 1200 and 2040 the same arm disagrees with
itself by 0.3-1.3 in margin, the same order as (and twice at 1200, larger than)
the cross-format delta; the two independent 2040 pairs gave 3.39 and 1.49, i.e.
the number you get depends on which pair of runs you compare. The engine does not
gain determinism as the prompt grows - it loses it, most likely because a 1200+
token prefill evicts and re-fetches experts through a ~9% hit-rate cache, so which
experts ran is part of the state that differs between processes.

What survives every run: **the argmax never changed**, at any length, in either
direction. So at the context cap a change of generated text still cannot be
attributed to KV precision - but neither can a precise KV-precision number be
quoted from one pair of runs; it needs many pairs, or a way to pin expert
routing (e.g. a fixed cache, `STRATA_EXPERT_CACHE=0`-style floor) so the arms
differ only in `--kv`.

### Pinning expert routing: what the existing flags could not do

Each attempt run twice per arm at 1200 tokens (int8), same prompt:

| setting | margin spread across 2 fresh processes |
|---|---|
| config as-is | 1.268 |
| `--adapt-every 0` (no adaptive tier swaps) | **0.337 - best achieved, 4x lower, not zero** |
| `--adapt-every 0 --sync-every-layer` | 0.365 |
| `--adapt-every 0 --pool-tasks 18` (fixed CPU partition) | 1.077 |
| `--adapt-every 0 --expert-cache 1` (no VRAM tier) | invalid: every logit came back `-inf` |

The residual is not the CPU partition, not async overlap and not the adaptive
tier alone: it is which code path an expert takes on a given run - VRAM tier or
CPU pool - because ~91% of experts live outside VRAM and a miss is served from
either depending on whether its copy landed in time. Pinning that needs an engine
mode where each expert always takes the same path (all-CPU or all-GPU), which no
flag provides; `--expert-cache 1` disables the tier but produced an all-`-inf`
row on this pack, so it is not a usable pin either.

### The noise-reduced sweep (all arms `--adapt-every 0`, two processes each)

| tokens | int8 margins | q4_0 margins | within-format spread | cross delta | argmax |
|---|---|---|---|---|---|
| 500 | 3.8025, 3.8025 | 3.7279, 3.7279 | **0.000** | **0.075** | same |
| 1200 | 10.968, 11.346 | 10.137, 12.337 | **0.379 / 2.201** | **0.831** | same |
| 2040 | 3.919, 6.893 | 6.174, 5.533 | **2.974 / 0.642** | **2.255** | same |

So even at the engine's quietest setting the user-visible curve is: 0.075 at
500, ~0.8 at 1200, ~2.3 at 2040 - while the same arm's own run-to-run spread is
0.0, 0.4-2.2 and 0.6-3.0. **Below roughly 700 tokens the KV difference is real
and well measured; above it the engine's noise is the same size as the effect,
and no single pair of runs can support a number.** The trend (a larger difference
at longer context) is what one expects from KV quantisation error, but this
engine cannot yet measure how large it is.

### The mode that does pin it: `STRATA_CPU_EXPERTS_ONLY=1`

Every consumer of residency asks `ExpertCache::slot_of`, so that one function is
where a hit and a miss are decided. With `STRATA_CPU_EXPERTS_ONLY=1` it returns
`kNotResident` for every expert (and `admit()` refuses every slot), so **every
expert is computed by the CPU pool and none from the VRAM tier**: the
"copy landed in time" race that made two runs take different kernels disappears.
It is an env mode, not a flag, and a measurement mode, not a default - it gives up
the VRAM tier on purpose.

Effect at 1200 tokens, int8, two fresh processes: spread **1.268 → 0.337 → 0.046
(best pair)**, i.e. the master source of the noise was indeed the expert path. A
residual remains, and it survives `--no-coupled-draft` (0.683) - so it is not the
draft proposals either.

### The pinned sweep (`STRATA_CPU_EXPERTS_ONLY=1 --adapt-every 0`, two processes each)

| tokens | int8 margins | q4_0 margins | within-format spread | cross delta | argmax |
|---|---|---|---|---|---|
| 500 | 3.8113, 3.8113 | 3.6880, 3.6880 | **0.000** | **0.123** (3.2% of margin) | same |
| 1200 | 10.914, 11.646 | 11.902, 12.178 | 0.732 / 0.276 | **0.988** | same |
| 2040 | 8.226, 7.674 | 6.221, 8.162 | 0.551 / 1.941 | **2.005** | same |

The curve is monotone - **0.12 → 0.99 → 2.00** - and at 1200 the effect is now
2-4x the noise instead of inside it. At 2040 they still overlap (q4_0's own two
runs differ by 1.94 against a 2.00 delta), so the cap remains the one length where
a single pair cannot support a number.

The residual noise grows with context (0 at 500, ~0.3-0.7 at 1200, ~0.6-1.9 at
2040) while routing is now fixed, which points at the long-context attention
accumulation rather than at expert dispatch: the same prompt over a longer KV
cache has more cells and more split reductions, and a reduction whose order
depends on scheduling is exactly what would leave a context-growing residue.
That is a kernel-level determinism question, and it is the next thing to test -
not something another flag will fix.
