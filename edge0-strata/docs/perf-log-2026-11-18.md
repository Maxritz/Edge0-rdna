**8 GiB rejected:** only 7,374 ranked complement experts fit, 0/1185 lend slots stay in RAM, so all
1185 re-read from disk each chunk — `gather 16,775 ms (62.6%)` of prefill. **28 GiB accepted on
4K:** all 43,846 blobs go by DMA, host staging just 33 ms, prefill/decode within noise of the arena
(−0.13% / −1.0%). NOTE: this is speed *parity*, not a speed win; the reason to ship it is the 896K
hard constraint.

**896K commit-exhaustion gate (`run_512k_mtp.ps1 -MaxContext 917504`, resident budget 28 GiB):**
exit 0 after 30 s. The engine itself printed `--resident-budget-gib 28.00 exceeds available commit
... 22.44 GiB`, clamped the pin to 22.43 GiB (leaving 4.1 GiB commit), kept `resident RAM 22.43 GiB`
and needed only 648 file blob reads. By contrast the default arena path needs a manual
`STRATA_ARENA_PIN_GIB=8` cap to survive 896K, and that cap costs prefill (~348 -> ~265 tok/s). Output
`248046 198 248045 74455`. Caveat: this differs from an earlier 896K gate's `715 1822 363 313`;
likely a prompt/config difference, so treat it as a liveness/commit check, not yet a byte-exact
896K golden token string.

Verdict: **mmap + 28 GiB pinned complement is a viable robustness config** (4K parity, automatic
commit clamp at 896K), not a throughput improvement. Not made a default yet — the harness pins
only the expert path; the KV cache and draft head still need their own commit headroom.

## Raw int4 / 3-bit format work: converter correctness bug found and fixed

The literal raw-int4/NVFP4 direction is blocked (no 512-expert high-precision latent source; only the
Q3_K pack exists), so the correctness-preserving substitute is a lossless natural-order 3-bit
repack (`tools/rdna2/raw3k_pack.py`) with a runtime GPU decode arm (`STRATA_A_RAW3K` in
`src/prefill/lat_q3k_fused.cu:160-200,298,541,821-824`).  Same 110 B/block, so no byte saving -
the hypothesis under test is decode complexity (five `lat_ld4` + funnel shifts -> one 6-byte load).

**Bug found during the first conversion:** the first converter decoded value `v` with
`qs[v//4] >> 2*(v%4)` and `hm[v//8] >> v%8`.  That is NOT ggml's Q3_K layout.  The production
kernel (`lat_q3k_fused.cu:202-238`) and `include/strata/artifact/dequant.hpp:242-274` both use
`qs[32*(v//128) + (v%128)%32] >> 2*((v%128)//32)` and high bit `hm[(v%128)%32]` at
`4*(v//128) + (v%128)//32`.  `raw3k_oracle.py` implements the ggml reference loop verbatim and
measured **44,395 code mismatches over 200 random blocks** with the naive formula, 0 with the
production formula.  The original `raw3k_verify.py` compared converter output against itself using
the same wrong formula, so its earlier "0 mismatches / 64 blobs" result was self-consistent but
proved nothing.  A partial 6.11 GiB bad pack was discarded.

**Fix:** `convert_gu` now uses the ggml/production permutation via 8 vectorised (half,t) slices,
and packs 8 codes -> 24 bits with shifts (no 768-bit intermediate), ~much faster than the original
fancy-index/gather form.  `raw3k_verify.py` now checks `decode_old` against `ggml_codes` on random
blocks first, then against the converter.  Verification after the fix:
- `raw3k_oracle.py`: 200 blocks, kernel-formula 0 mismatches, naive 44,395.
- `raw3k_verify.py` on 128 real blobs: 209,715,200 values, **0 mismatches**, scales+d identical.
- `raw3k_gpu_check.py`: 512 random super-blocks through ggml code -> converter -> the exact GPU
  `nat[0..3]` / `__vsub4` extraction, **0 mismatches**.

### Final verdict: REJECTED (correctness + performance)

Full pack converted: `E:\Edge0-120B-raw3k\experts.bin` 28,626,124,800 B (exactly the
q3k size) with all 48 small sidecars present. Written-pack spot check: 9 scattered
blobs / 14.7 M values, 0 code mismatches, scales and d identical. Direct GPU decode
test with the full engine define set: 10 real super-blocks, 0 staged mismatches.

**End-to-end A/B, 5 alternating pairs** (`ab_raw3k.csv`): every A arm emitted the
canonical `248046 198 248045 74455 198 248068 198 760`; every B arm emitted
`66 3045 84 3045 911 319 3217 3045` (var4 ends `87`). `TOKEN_VARIANTS=3`.
The byte-exact gate fails on all five pairs.

| arm | prefill tok/s | gate/up ms | blobs |
|---|---|---|---|
| A (q3k) | 343.33 / 344.54 / 344.69 / 341.71 / 342.70 | 3827 / 3824 / 3827 / 3829 / 3860 | 43774 |
| B (raw3k) | 344.18 / 343.38 / 341.45 / 341.47 / 341.93 | 3877 / 3869 / 3882 / 3868 / 3861 | 43774 |

Same blob count, same workload: gate/up is consistently 40-50 ms **slower**, so
replacing five funnel-shifted loads with one 6-byte load is a regression here
(the 110 B pitch alternates the 6-byte field's alignment). No speed case exists.

**Runtime symbol proven healthy:** a 3-pair env-only A/B with `STRATA_A_RAW3K=1`
on the *original* q3k pack gave A canonical, B `82 220 248046 198 248045 846 198
248046` (`TOKEN_VARIANTS=2`) and 37,926 blobs (vs 43,774) — the decoder is applied,
so the symbol path is not the cause. All small sidecars between the two packs hash
identical; only `experts.bin` differs. A minimal `cudaMemcpyToSymbol` readback
could not run while the harness held the GPU; it is not needed for this verdict.

**Root cause of the end-to-end failure:** decode does not use the fused GPU GU
kernel. B's log shows `verify window ... CPU experts 8.77 distinct / 8.77 routed
per layer`, `the CPU expert pool 19.396 ms/token ... (1 positions, 48 dispatches)`
and `expert blobs 49820 blobs read`. That pool reaches
`native_gu_rows_impl` (`src/kernels/cpu/native_expert.cpp:372`), whose only
specialised gate/up arm is `STRATA_KQ256` for **Q4_K (type 12)**; Q3_K (type 11)
falls through to ggml's `vec_dot_q3_K` / `dequantize_q3_K`, which is raw3k-unaware.
`lat_q3k_gu.cu` and `moe_fused_q3k.cu` contain two further raw3k-unaware Q3_K
decoders. Making raw3k shippable therefore needs a second, AVX2-native CPU
decoder plus an audit of every Q3_K consumer - for **zero byte saving** (still
110 B/block) and a measured prefill regression.

A one-emitted-token run (`--spec 2 --max-new 1`, A `248046`, B `66`) was intended
to isolate prefill, but its log shows a 1-position CPU expert verify window, so it
does not isolate the GPU prefill path; it is consistent with the CPU-decoder cause.

**Action:** the `STRATA_A_RAW3K` arm (63 insertions) was reverted from
`src/prefill/lat_q3k_fused.cu` and the canonical binary rebuilt. The converter,
oracle, verifier and pack remain on disk as untracked evidence only - not shipped.

## Code-inspection findings (no code changed)

- **Option 2, bulk-decode staging:** not implemented. `RouterLookahead` (`expert_source.cpp:3203-3329`)
  predicts expert IDs and warms raw source pages / Foresight slots; it never computes expert
  outputs. The CPU pool (`pool.cpp:1233-1387`) computes the *current* layer's routed set at use
  time and is already bound by RAM traffic (~27.6 ms, 30.6 GB/s, `perf-log-2026-11-16.md:328-339`).
  Ahead-of-use decode cannot remove that byte traffic — it would only move it in time, and needs
  new buffer lifetime/invalidation/fallback machinery.
- **Option 4, contiguous H2D coalescing:** already refuted in-tree (`prefill.cpp:408-413`,
  `edge-0-analysis-rdna2.md:563-587`): the copy engine is ~85% idle, ring-starved, not link-bound;
  28 GB/s is reached with blob-sized transfers. File-read coalescing (`copy_blobs` 32 MiB merge)
  is already shipped. No new A/B was run for this reason.
- **Staged-launch batching:** already landed. `STRATA_LAT_STAGED_BATCH` now defaults to 32
  (`prefill.cpp:1584-1600`); `lookahead = stage_n - stage_batch` (`prefill.cpp:6220`) implements
  the prerequisite that made the earlier batching experiment corrupt output. The code records
  byte-identical 128-slot results (batch 32: 255.57/255.69 tok/s vs batch 16: 250.48/250.29).
- **Interleaved / alternate-line read:** not feasible as a byte reduction. The gate/up kernel
  (`lat_q3k_fused.cu:229-303`) reads all 640 gate + 640 up rows × 550 B, the down kernel
  (`lat_q3k_down.cu:154-234`) all 1280 rows × 360 B — exactly 1,164,800 B per used expert.
  `on0/on1` mask activations and output rows, never weight bytes. Gate and up are 352,000 B
  apart in the native blob; interleaving them changes placement, not the byte count. No
  measurement attributes this kernel's time to global coalescing; the measured limiter is LDS
  read bandwidth. Stride padding was tried and cost +48% (`lat_q3k_fused.cu:73-80`).
- **Down-kernel activation-word hoist — VERDICT: no signal, rejected.** The GU kernel's measured
  -2.6 % hoist (`lat_q3k_fused.cu:379-395`) was mirrored into `lat_q3k_down.cu` behind a
  `STRATA_A_DOWN_HOIST` template arm so both variants lived in one binary. 5 alternating pairs
  (`ab_downhoist.csv`): `gemm down` A 1046/1046/1045/1046/1045 ms (mean 1045.6) vs B
  1046/1045/1046/1045/1050 ms (mean 1046.4), +0.08 % - inside the 2 % arm spread.
  Prefill means 349.61 (A) vs 349.41 (B) tok/s, +0.06 %; `TOKEN_VARIANTS=1`, canonical tokens.
  The measured down cost (~8.9 % of the GPU timeline) is not the inner dp4a instruction count.
  The arm was reverted and the canonical binary rebuilt.
- **Low-bit / RISC correctness — VERDICT: research project, not a packer toggle.** The "RISC
  computer" is `third_party/Kraken-x/{include/krk/rv32.hpp,src/rv32.cpp}` — a host-side RV32I+M
  integer emulator with a `VDOT` int4-code×signed-byte dot instruction (`rv32.cpp:321-345`). It
  never runs in a transformer forward, never routes or samples, and has **no Q3_K decoder**. Its
  only low-bit correctness use is `tools/ta_act_recovery.cpp:32-67`, a narrow oracle proving
  RV32's integer dot equals native TQ1_0×q8 after an explicit transcode to `code-8` int4. There
  is no RV32 call site anywhere in Edge0 latent prefill/kernels/pack code. The latent path is a
  closed exact contract: Q3_K gu (type 11) + IQ4_NL down (type 20), 1280-wide, 1,164,800 B blob,
  80-B staged-int8 row, 550-B row pitch, 800-B staged H row, with ggml-dequant and `memcmp`
  gates (`q3k_real_ref.cpp`, `lat_q3k_fused_test.cpp`). Lowering bits requires a new pack layout
  + producer (the referenced `make_latent_a_q3k.py` is absent from the repo), a new device
  decoder into the 80-B row, new CUDA-mma and RDNA2-dp4a kernels, new H/down contracts, new
  correctness tests and validation gates across `expert_layout_load`, `native_fmt`,
  `native_expert_supported`, `generate.cpp` and the serve delegate registry. `expert_nibble.hpp`
  ("lossless" 4-bit) is a different CUDA sm_60 2560-wide IQ2_S/IQ3_XXS/IQ3_S path, off by default,
  and cannot feed the 1280-wide latent stage. `iq_pack.py` writes raw GGUF slices and has no
  transcode. GGUF low-bit ids exist (Q2_K 10, IQ2_* 16/17/22, TQ1_0/TQ2_0 34/35, Q2_0 42,
  NVFP4 40, MXFP4 39, plus trellis 143-149) but Strata scalar dequant exists only for Q4_0,
  Q2_0, Q3_K, Q4_K, IQ4_NL, IQ4_XS — and `native_fmt` needs a ggml vec_dot for both types.
  Bitnet/TQ1 builders live in Kraken dense tools (`make_bitnet_gguf.py`), not latent experts.
  A pack in a new format would also produce different weights from Q3_K, so byte-identical output
  is impossible by construction; only a KL/top-1 gate could judge it.
